# 판정 규칙 (rules)

## 왜 만드는가

실험 1~4 이후에도 남은 오답은 답변 모델이 원문을 매번 새로 해석하면서 생긴다.

- 예외 조항: 휴학생 제외, 단 방통대는 가능
- 이름이 비슷한 항목: 건강보험료와 보험료 납부
- 조건: 계좌이체는 증빙을 내야 인정

모델 교체나 프롬프트 규칙 추가로는 줄지 않았다. 근거는 [EXP4_CONCLUSION_LINE_DEV.md](../../benchmarks/EXP4_CONCLUSION_LINE_DEV.md)에 있다.

## 결정 사항

- **무엇이 있는가**는 YAML 메타데이터로 선언한다.
  - 대상: 지출 항목, 결제 방식, 사용 불가 업종, 자격 요건, 제외 대상, 자격 상실 사유
  - 각 항목에 쪽수와 원문 인용을 붙인다.
- **어떻게 판정하는가**는 핸들러 코드가 맡는다. 결정적으로 동작하고 단위 테스트를 둔다.
- **LLM은 두 가지만 한다.**
  - 질문을 선언된 규칙 ID에 연결한다.
  - 핸들러가 정한 결론을 바꾸지 않고 문장으로 쓴다.
- 규칙에 걸리지 않는 질문과 정보성 질문은 기존 RAG 경로로 간다.
- 범위는 판정 질문만이다. 지출(8·12~18·31쪽)과 자격(7·9쪽)을 다룬다. 책자 전체를 모델링하지 않는다.
- 시험셋 실패 문항만 골라 규칙을 만들지 않는다. 해당 쪽 전체를 옮긴다.
- 원문 인용은 `tests/test_rules.py`가 OCR 원문과 대조해 검사한다. `Data/`가 없는 환경에서는 건너뛴다.
- 인덱스와 청킹은 바꾸지 않는다. 고정 기준선 인덱스 `18fec50`을 그대로 쓴다.
- 기존 결과와 비교할 수 있도록 스위치를 둔다(`RULES_ENABLED`, 예정).

## 남은 일

1. [ ] **규칙 검토 (사람):** 판정, 이름, 별칭(`aliases`, 책자에 없는 표현)을 확인한다. 특히 `note`가 붙은 항목을 본다.
2. [ ] **핸들러**
   - `resolve_spending(item, payment)`
   - `check_eligibility(...)`
   - 단위 테스트
3. [ ] **질문 → 규칙 연결기:** 구조화 출력을 쓰고, 선언된 ID와 "해당 없음" 중에서만 고르게 한다.
   - 개발셋으로 두 가지를 잰다: 연결 정확도, 규칙으로 처리된 비율.
4. [ ] **워크플로 연결**
   - 규칙에 걸리면 결정적 결론을 내고, 아니면 RAG로 보낸다.
   - 규칙으로 대체되는 특수 처리를 지운다: 배달앱 지침, 키워드 차단 목록, 평가기 도메인 규칙 등.
5. [ ] **측정:** 개발셋 → 시험셋 3회. 보고서는 `benchmarks/EXP5_*.md`.
