# 실험 1: 키워드 차단 확인기

기준선([BASELINE_V1.md](BASELINE_V1.md))과 같은 시험셋, 같은 고정 인덱스, 같은 판정자로 측정했다. 조건마다 3회 실행했다.

## 1. 기준선의 문제

- 정상 질문 17개 중 15개가 과잉 차단됐고, 이 중 10개는 `policy.py`의 키워드 사전 차단 때문이었다.
- 차단 규칙은 질문 어디에든 키워드가 있으면 막는다. 그래서 아래 두 경우도 막혔다.
  - 키워드를 비교로만 언급한 질문: "명품은 **안 된다던데** 면접 구두는?"
  - 키워드가 지출 대상과 무관하게 쓰인 질문: "**게임** 회사 면접 정장"
- 짝 문항 t093(차단됨) / t042(정상 답변)는 같은 사실을 묻는데 키워드 유무로 결과가 갈렸다.

## 2. 해결

- 키워드가 걸리면 LLM 확인기(`app/rag/blocker_check.py`)가 한 번 더 판단한다.
  - 먼저 사용자가 실제로 돈을 내려는 대상과 결제 방식을 뽑는다.
  - 후보 제한마다 두 가지를 따로 판단한다: 지출 대상이 제한 항목 자체인가, 결제 방식이 제한 방식 자체인가.
- 두 판단이 모두 명시적으로 `false`일 때만 차단을 푼다.
  - LLM 호출 실패, 출력 오류, 후보 key 누락이면 차단을 유지한다.
  - 사용 불가 항목을 허용하는 실수가 과잉 차단보다 비싸기 때문이다.
- 키워드 차단은 사전 점검에서만 판단한다.
  - 근거 평가 뒤의 최종 판단은 같은 문서를 다시 보므로 근거 평가 결과만 쓴다.
  - 같은 문서로 다시 검사하면 풀어 준 차단이 되살아난다.
- `BLOCKER_CHECK_ENABLED=false`면 기존 키워드 차단으로 돌아간다(비교 실험용).

### 개발 과정 (개발셋만 사용)

- **개발셋 구성**
  - 기존 개발셋에는 키워드가 들어간 정상 질문이 거의 없었다. 그래서 정상 질문 20개를 새로 썼다(`policy_keyword_dev_v1.jsonl`).
  - 실제 차단 질문 22개는 기존 `policy_safety_v2_150`에서 가져왔다.
  - 시험셋과의 최대 유사도는 임베딩 코사인 0.67이다. 0.7에 가깝던 2문항은 교체했다.
- **모델 선택**
  - 확인기만 단독으로 돌려 비교했다. 서비스 모델 `gpt-4o-mini`는 프롬프트를 고쳐도 42문항 중 5~6개를 틀렸다.
    - 실제 차단 1개를 푼 적도 있다.
    - temperature 0인데도 틀리는 문항이 실행마다 달랐다.
  - 같은 프롬프트로 `gpt-4.1-mini-2025-04-14`는 0개를 틀렸다. 그래서 확인기만 이 모델을 쓴다(`OPENAI_BLOCKER_CHECK_MODEL`).
- **개발셋 결과 (전체 챗봇 경로, 1회)**
  - 키워드로 차단된 정상 질문: 16/20 → 0/20.
  - 실제 차단 유지: 21/22 → 21/22.
  - 놓친 1개(중고 노트북을 당근마켓에서)는 두 조건 모두 의도 분류기가 일반 질문으로 보낸 경우다.
  - 프롬프트와 모델을 이 개발셋으로 골랐으므로, 이 수치는 낙관적이다.

## 3. 지표를 고른 이유

- **주 지표와 대항 지표:** 기준선과 같은 사전 등록 지표를 쓴다([EVAL_V1.md](EVAL_V1.md)). 이번 변경의 목표 지표는 과잉 차단률이다. 차단을 푸는 변경이므로 위험 허용률을 함께 본다.
- **반복 실행 (3회):** 쿼리 생성과 답변 생성이 실행마다 달라지기 때문이다. 기준선 3회 사이에서도 109문항 중 15개의 라벨이 바뀌었다. 1회 비교로는 몇 문항 차이가 효과인지 우연인지 구분할 수 없다.
- **"한 번이라도 위험"을 따로 센 이유:** 가끔만 "된다"고 답하는 문항이 있다. 평균만 보면 이런 위험이 묻힌다.

## 4. 결과 (시험셋, 조건별 3회)

| 지표 | 기준선 (3회) | 확인기 (3회) |
|---|---|---|
| **과잉 차단 ↓** (n=17) | 15, 14, 15 (평균 14.7) | **6, 6, 9 (평균 7.0)** |
| 결론 정확도 ↑ (n=73) | 36, 39, 39 (평균 38.0) | **46, 49, 44 (평균 46.3)** |
| 위험 허용 ↓ (n=19) | 1, 1, 1 | 1, 0, 1 |
| 한 번이라도 위험 허용 (n=19) | 1 (t073) | 1 (t069) |
| 지어내기 ↓ (n=10) | 2, 1, 1 | 2, 2, 1 |
| 실행 간 라벨이 바뀐 문항 (n=109) | 15 | 18 |
| 키워드 문항 응답 시간 p50 / p95 | 4.3초 / 7.7초 | 7.1초 / 9.7초 |

- **과잉 차단과 결론 정확도:** 두 조건의 3회 범위가 겹치지 않는다(과잉 차단 14~15 vs 6~9, 정확도 36~39 vs 44~49).
  - 과잉 차단의 감소는 코드 경로가 바뀐 결과다. 정상 질문 10개가 `blocked_by_policy`로 끝나던 것이 0개가 됐다.
- **안전:** 키워드 차단으로만 막던 사용 불가 문항 5개(t078~t082)는 확인기 조건 3회 모두 차단을 유지했다.
- **위험 허용:** 두 조건 모두 실행당 0~1개라 차이를 말할 수 없다. 다만 위험하게 답한 문항이 조건마다 달랐다.
  - t073(피부과 레이저): 기준선 3/3에서 "가능", 확인기 0/3.
  - t069(대학원 등록금): 기준선 0/3, 확인기 2/3에서 "가능".
  - 두 문항 모두 키워드가 없다. 그래서 두 조건에서 같은 코드 경로를 탄다. 차이를 만들 원인을 코드에서 찾지 못했다.
  - 실행 간 라벨이 바뀌는 문항이 15~18개이므로, 3:0으로 갈리는 문항이 우연히 1~2개 나오는 것은 이상하지 않다.
  - 6회를 합치면 사용 불가 19문항 중 **2개(t069, t073)가 가끔 "된다"고 답한다**. 이번 변경과 무관한 시스템의 위험이다.
- **응답 시간:** 키워드 문항의 p50이 약 2.8초 늘었다.
  - 원인 1: 확인기 호출이 추가됐다.
  - 원인 2: 기존에는 즉시 나가던 차단 문구 대신 답변 생성까지 가게 됐다.
- **남은 과잉 차단 6~9개는 원인이 다르다**(1회차 기준).
  - 의도 분류기가 일반 질문으로 보냄: t096.
  - 근거 부족으로 답을 피함: t097, t098, t099.
  - 답변 모델이 체크카드 직접 결제를 간편결제로 오해함: t105, t108.

## 5. 한계

- **표본이 작다.** 범주별 n이 17~19다. 위험 허용처럼 0~1개를 다투는 지표는 3회로도 차이를 판별할 수 없다.
- **기준선 재실행의 조건이 조금 다르다.** 기준선 2·3회차는 현재 코드에서 스위치를 끄고 돌렸다. 1회차는 기준선 커밋 `ae1eccf`에서 돌렸다.
  - 최종 판단에서 키워드 검사를 뺀 것 외에는 키워드 차단 경로가 같다. 같은 문서를 보는 한 결과도 같다.
- **실행 환경이 겹친다.** 2·3회차는 네 실행을 동시에 돌렸다. 그래서 전체 응답 시간은 1회차보다 길다. 응답 시간은 같은 시각에 돌린 조건끼리만 비교한다.
- **확인기 모델이 다르다.** 확인기는 서비스 답변 모델보다 강한 모델이다. 판정자(`gpt-4.1`)와 같은 계열이지만 판정자는 답변의 결론만 분류하므로 직접 겹치지는 않는다.
- **분석자가 시험셋을 봤다.** 확인기 프롬프트의 예시는 제한 항목 이름(게임 아이템, 포인트 충전 등)을 일반화한 것이다. 시험 문항을 옮기지는 않았지만, 분석자는 시험셋 실패 사례를 본 상태였다.

## 재현

```bash
cd backend
# 확인기 조건 (기본값)
python -m benchmarks.run_eval_v1 answer --execute --tag blocker_check
# 기준선 조건
BLOCKER_CHECK_ENABLED=false python -m benchmarks.run_eval_v1 answer --execute --tag baseline_r2
# judge, score 단계를 같은 --tag로 실행한 뒤
python -m benchmarks.aggregate_eval_v1 baseline=baseline,baseline_r2,baseline_r3 \
    blocker_check=blocker_check,blocker_check_r2,blocker_check_r3
```

검색 결과 파일은 검색 코드가 바뀌지 않아 기준선 것을 복사해 썼다(`eval_v1_<tag>_retrieval.jsonl`).
개발셋 비교는 `python -m benchmarks.run_keyword_dev --execute`로 실행한다.
