# 실험 3b: 사용 불가 목록 대조 (질의 + 근거 평가 규칙)

비교 대상은 실험 2(BM25 2글자 토큰) 3회다([EXP2_BM25_BIGRAM.md](EXP2_BM25_BIGRAM.md)).
시험셋, 고정 인덱스, 판정자는 같고, 답변과 판정을 3회 실행했다.
이번 변경은 원 질문 검색을 바꾸지 않아서 검색 단계 결과는 실험 2 것을 그대로 썼다.

## 1. 기준선의 문제

- 실험 2에서 t069(대학원 등록금)와 t073(피부과 레이저)이 3회 모두 "가능합니다"로 답했다.
  - 두 답변의 근거는 사용 가능 항목 청크(교육비, 의료비)뿐이었다.
- 사용 불가 문항 중 정답 근거가 답변 생성 출처에 들어간 비율은 6~7/19였다.
- 실험 3a([EXP3_TABLE_SPLIT_DEV.md](EXP3_TABLE_SPLIT_DEV.md))에서 확인한 원인:
  - "X에 써도 되나요?"는 임베딩상 사용 가능 항목과 가깝다. 그래서 사용 불가 업종 목록이 검색되지 않는다.
  - 반면 "청년수당 클린카드 사용 불가 업종 X" 질의는 표를 9/9 찾았다.

## 2. 해결

1. **목록 대조 질의 추가.** `build_search_queries`가 "청년수당 클린카드 사용 불가 업종 + (재작성 질문)" 질의를 항상 2번째에 넣는다.
   - 검색 결과를 질의별로 번갈아 합친 뒤 8개로 자르기 때문에, 뒤에 두면 잘린다.
   - 최대 질의 수는 5개에서 6개로 늘렸다.
2. **근거 평가 규칙 추가.** 평가 프롬프트에 두 규칙을 넣었다.
   - "근거로 '불가'라고 답할 수 있으면 충분하다."
   - "질문 대상이 사용 불가 목록에 있으면 direct로 보고 그 청크를 출처에 넣는다."
3. 검색 결과가 바뀌므로 캐시 namespace를 `rag:v7`로 올렸다.

### 개발 과정 (개발셋만 사용)

- **개발 표 질문 18개 (전체 챗봇 경로)**

| 단계 | 표가 답변 출처에 포함 | 판정 라벨 |
|---|---|---|
| 변경 전 | 6/18 | DENY 7, NO_INFO 11 |
| 질의만 추가 | 4/18 | DENY 6, NO_INFO 12 |
| + 평가 규칙 | **17/18** | **DENY 18** |

- **질의만으로 효과가 없었던 이유:** 단계별로 추적하니 검색은 표를 찾았다. 그런데 평가기가 이유 칸에는 "노래방은 사용 불가 업종에 포함되어 불가"라고 쓰고도 `is_sufficient=false`로 판정했다. "답이 불가"를 "답할 수 없음"으로 처리한 것이다. 그래서 평가 규칙을 같은 개입에 포함했다.
- **부작용 확인 (키워드 정상 질문 20개):**
  - 과잉 차단(DENY + NO_INFO)은 12개에서 10개로 줄었다.
  - 대신 잘못된 "불가"가 3개 새로 생겼다(도박 중독 상담, 대중교통 교통비, 유흥가 근처 독서실).
  - n과 실행 간 편차로는 판별할 수 없어서 시험셋 3회로 판단하기로 했다.

## 3. 지표를 고른 이유

- **주 지표:** 위험 허용(실험 2에서 나빠진 지표).
- **대항 지표:** 과잉 차단. 평가 규칙이 "불가" 답을 쉽게 만들기 때문에 함께 본다.
- **보조 지표 "근거가 답변 생성 출처에 들어갔는가":** 사전 등록만 하고 구현하지 않았던 지표를 이번에 구현했다(`score_source_evidence`). 원 질문 검색 Hit@5는 이번 변경으로 바뀌지 않으므로, 실제 답변 경로에서 근거가 전달됐는지를 직접 본다.

## 4. 결과 (시험셋, 조건별 3회)

| 지표 | 실험 2 | 실험 3b |
|---|---|---|
| **위험 허용 ↓** (n=19) | 2, 2, 2 | **0, 0, 0** |
| 한 번이라도 위험 허용 | t069, t073 | 없음 |
| 과잉 차단 ↓ (n=17) | 6, 5, 5 | 6, 5, 4 |
| 지어내기 ↓ (n=10) | 2, 1, 1 | 1, 1, 2 |
| **결론 정확도 ↑** (n=73) | 46, 49, 49 | **56, 56, 55** |
| 근거가 답변 출처에 포함 – 전체 (n=99) | 56, 58, 58 | 67, 65, 64 |
| 근거가 답변 출처에 포함 – not_allowed (n=19) | 6, 7, 7 | 10, 12, 10 |
| 응답 시간 p50 | 14.2~14.7초 | 16.6~16.9초 |

- **위험 허용과 결론 정확도:** 두 조건의 3회 범위가 겹치지 않는다.
- **과잉 차단과 지어내기:** 범위가 겹친다. 개발셋에서 걱정한 잘못된 "불가"는 시험셋 과잉 차단을 늘리지 않았다.
- **결론 정확도 범주별 (3회):**

| 범주 | 실험 2 | 실험 3b |
|---|---|---|
| not_allowed | 10, 10, 11 | 16, 14, 15 |
| conditional | 13, 14, 13 | 15, 17, 15 |
| 나머지 범주 | — | 변화가 실행 간 편차 안이다 |

- **3회 중 2회 이상 결과가 바뀐 문항:**
  - 좋아짐: t069, t073(ALLOW → DENY), t050, t057, t059, t064, t065, t072(NO_INFO 또는 혼재 → DENY).
  - 나빠짐: **t082**(토스 포인트 충전, DENY ×3 → NO_INFO ×3).
- **t082가 나빠진 이유:**
  - 키워드 질문이라 쿼리 생성기를 건너뛰고 정책 검색 질의만 쓴다. 그래서 이번 목록 대조 질의가 붙지 않는다.
  - 정책 검색 질의로는 "결제 포인트 구매, 충전식 결제"가 있는 청크(sem_0032)가 검색되지 않는다.
  - 실험 2의 "불가"는 이 규정이 아니라 "사용 가능 항목에 없다"는 추론이었다.
  - 키워드 경로에도 목록 대조를 넣는 것은 다음 후보로 남긴다.
- **응답 시간:** p50이 약 2.2초 늘었다. 원인은 두 가지다.
  - 질의가 하나 늘어 검색이 한 번 더 돈다.
  - "확인 불가" 고정 문구 대신 답변을 생성하는 경우가 늘었다.

## 5. 한계

- **n이 작다.** 위험 허용은 n=19다. 이 실험의 개선은 같은 두 문항(t069, t073)이 3회 모두 바뀐 결과다.
- **분석자가 시험셋을 봤다.** 이 개선은 실험 2의 시험셋 실패 분석(t069, t073)에서 출발했다.
  - 원인 진단과 수정 검증은 개발셋으로 했고, 개발 질문은 시험셋에 없는 업종으로 썼다.
  - 하지만 방향 자체는 시험셋 실패를 보고 정했다. 그러므로 이 결과는 시험셋에 대해 낙관적일 수 있다.
- **평가 규칙의 부작용은 덜 확인됐다.** 개발셋에서는 잘못된 "불가"가 3개 생겼다. 시험셋 정상 문항(n=17)에서는 늘지 않았지만, 실제 사용자 질문에서 과잉 거절이 늘 가능성은 남는다.
- **정보 문항 답변은 검증하지 않았다.** 목록 대조 질의가 정보성 질문에도 붙어 잡음 청크가 섞일 수 있다. 정보 문항의 답변 사실성은 v1에서 재지 않는다.
- **편차가 크다.** 실행 간 라벨이 바뀐 문항은 18개로, 이전 실험과 비슷한 수준이다.

## 재현

```bash
cd backend
for t in restriction_query restriction_query_r2 restriction_query_r3; do
  cp benchmarks/results/eval_v1_bm25_bigram_retrieval.jsonl benchmarks/results/eval_v1_${t}_retrieval.jsonl
  python -m benchmarks.run_eval_v1 answer --execute --tag $t
  python -m benchmarks.run_eval_v1 judge --execute --tag $t
  python -m benchmarks.run_eval_v1 score --tag $t
done
python -m benchmarks.aggregate_eval_v1 bm25_bigram=bm25_bigram,bm25_bigram_r2,bm25_bigram_r3 \
    restriction_query=restriction_query,restriction_query_r2,restriction_query_r3
```
